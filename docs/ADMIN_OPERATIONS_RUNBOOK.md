# V2.5 運営手順（staging検収版）

## 通報
1. 未対応一覧を優先度順で確認。個人情報の公開疑いを先に確認する。
2. 対象詳細を確認し、確認中へ移す。必要な対象だけ非表示にする。
3. 必要な理由・短い内部メモを記録する。メール/住所/秘密値/元の個人情報をメモへコピーしない。
4. 非表示とは別に、対応済み/対応不要を選ぶ。誤操作は現在の版を読み直して再表示する。
5. 競合時は再読込。通信失敗の再試行は同じ操作IDで二重適用されない。内容を変える場合は新操作ID。

## 利用停止
公開作品や共同制作履歴は保持する。本人の新規書込を止めるための一時措置。永久BAN/内容改変はしない。解除前に原因を確認し、理由と監査を残す。運営者の権限剥奪はOwnerの権限管理から行う。

## 緊急停止と復旧
Ownerが対象と影響、未完了処理、DB/環境変数両方の状態を確認し、最小のスイッチを止める。global停止より必要に応じルーム単位停止を使う。停止確定前に開始したDB書込と外部送信は完了する可能性がある。起動設定OFFの処理を管理画面で勝手にON扱いしない。

AI停止: 既存epoch stopで未完了taskを無効化し、人間の作成を維持する。provider出力の後着は既存lease/epoch検査で拒否。実OpenAI429を手動連打しない。
公開停止: DB公開RPCを止める。作品本文の修正や生成を行わない。復旧後は締切超過分が通常処理対象になるため、件数と設定を先に確認。
退会: 受付とworkerの両方を必要範囲で止める。prepared/auth_unknown/needs_reviewと外部副作用checkpointを照合する。started/unknownの未完了がある場合はUIから再開しない。Auth削除は最後、手動force削除やジョブの書換えは禁止。外部処理の真偽が不明なら停止維持して担当者へ判断を求める。

## 監視
日/7日/30日のメタデータと滞留を確認。AIの失敗・lease切れ、課金past_due/grace、pending Webhook、invalid signature、重複/順序逆転の観測、退会キューを確認。0件と未取得を区別。cronの観測なしは正常を意味しない。Supabase管理Auth/SMTPログはこの画面で自動検証しない。

## 環境・権限
この版の許可先はfwqucffxdmbdczspkcyrだけ。本番への適用は別承認と移行検収が必要。Owner初期登録はDB担当者の手順で行い、email照合や公開APIでの自己昇格を用意しない。通常は最小人数のModeratorを使用し、不要時に解除。変更時のsession freshnessを満たさなければログアウト/再ログイン。MFAは将来の運用課題として残す。

## 検収後
一時Preview Cookie/認証sessionを終了し、browser/local server/forwarderを停止。テストのため変更した停止状態は開始時へ戻す。残す合成fixtureと削除しない監査を記録。秘密値はログ/docs/Gitへ出さない。
