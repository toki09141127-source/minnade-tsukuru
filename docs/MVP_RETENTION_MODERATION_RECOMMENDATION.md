# 100人MVP：退会・共同作品・名義・通報の推奨案

作成：2026-10-21。Status: USER APPROVAL REQUIRED（提案。未採用・未公開・未適用）。この文書の期間は運用の仮案であり、法定期間や既に保証できるサービス水準ではない。

## 推奨する基本方針

共同作品と参加者のアカウントを分ける。退会は本人の認証・公開プロフィールを終了し、既に共同制作へ提供した作品・素材は、説明して同意を得た必要な許諾の範囲で公開・制作を継続する。氏名表示・権利侵害・個人情報・安全上の申立ては別途審査し、「共同作品だから絶対消せない」と扱わない。
100人MVPでは外部転載・商用利用・広告転用の権利を拡張しない。本人の明確な同意なしに生成AI学習へ利用しない方針候補も維持する。退会を著作権の運営への譲渡と扱わず、creator/coreという役職も著作権の帰属を決めるものではない。

## 退会後に残すもの・切り離すもの

- Auth：確認済み本人の退会申請を受け、まず新規操作を停止する。アプリとDBで停止状態を判定し、既存JWTによる操作も拒否する。Auth user削除だけで全sessionが即時無効になると仮定しない。
- 公開プロフィール：受付後は公開停止する案。bio/SNS/外部リンク/画像/メールとの関連は原則削除対象。旧プロフィールURLから別人へリダイレクトしない。
- 公開名義：退会画面で「退会した参加者へ変更」を推奨選択肢として提示し、変更を本人に明示確認する。「指定したペンネームだけ残す」は別の明示選択。残す場合もプロフィールリンク/email/Auth IDは付けない。新規同意のない既存投稿へ遡及して一括変更しない。
- 投稿・作品：許諾が確認できる共同作品、制作ログ、作品に組み込まれた素材は原則保持。本文・引用・画像内の名前や連絡先まで自動的に消えるわけではないため、個別の秘匿/編集/差替え申請を用意する。「退会した参加者」表示だけを法的な匿名化完了とは呼ばない。
- likes：本人の操作履歴との結び付きを削除する案。集計値が減る可能性を許容する。作品の作者/本文は連動削除しない。
- membership/承認履歴：アクティブ参加資格を終了。作品に必要な寄与記録は公開用の非認証author identityに分離する設計候補。既存auth FKをそのままCASCADEさせるだけでは不足。
- 添付：使用済みobjectは作品に従い保持。owner退会だけで一括Storage削除しない。未使用uploadは仮TTL24時間でcleanup対象にするが、worker/leaseの検収前には自動削除を有効化しない。
- 通報・監査：一般公開せず、目的と期限を定めて限定保持。誰が何をしたかの識別情報を永久保存しない。IDやハッシュも関連付け可能なら個人情報上の検討対象にする。

名義表示は著作者の意思と関係するため、規約だけで無条件に名義変更できると決めない。[文化庁の氏名表示権の説明](https://www.bunka.go.jp/chosakuken/keiyaku_manual/1_1_3.html)を踏まえ、退会時の選択・既存許諾との整合を専門家に確認する。

## 進行中ルーム・creatorの退会

coreの5分退出制限やcreator退出不可という現在のroomルールを、アカウント削除/個人情報の申立てを拒絶する理由にしない。一方、退会により他人の投稿まで消したり即時公開したりしない。
creator退会時は、残るcoreに進行役の引継ぎ意思を確認する案。運営が黙って任意の参加者をcreatorへ昇格させない。引継ぎは権利の譲渡ではない。権利・安全上の問題がなければ元の期限を維持し、関係者の許諾確認が取れない場合は運営が暫定非公開にして期限公開対象から外す設計にする。
引継ぎ/公開保留/復旧の管理手順は未実装。採用決定後、既存role/FK/cronとの整合を別途レビューする。

## 削除・保持期間の仮案

1. 本人確認後の公開プロフィール停止と新規操作停止：受付処理で実施する設計。現実装には未搭載。
2. 通常の退会処理完了：申請から30日以内を内部目標。未完了時は理由・残る対象・次回連絡日を通知し、完了していないのに成功表示しない。安全な再実行を可能にする。
3. 認証情報/プロフィール等のprimary削除：処理完了までに実施。共同作品の保持例外を本人へ一覧で説明する。
4. 退会処理の最小監査記録：完了後90日で消去/必要性再判定する案。作品許諾の証拠は、作品公開継続に必要な最小項目を別管理し、連絡先/退会理由を流用しない。許諾証拠の保存方法・終了条件は専門家確認。
5. 解決済み通報の通常証拠：解決/異議処理終了後90日で削除。記録には対象ID、分類、判断、日時、担当を残し、本文コピーは必要箇所だけ。
6. 利用停止の再発防止情報：原則180日ごとに見直す案。必要性なく永続ブラックリスト化しない。長期停止が必要な案件は理由・対象・次回見直しを決裁する。
7. 運用ログ：原則30日。本文/メール/token/署名URLを通常ログに入れない。
8. バックアップ：最大90日以内に自然消去する案。ただし実providerの保存・復元仕様を確認してから公表する。復元時には削除済み対象を再消去する台帳を照合し、公開を再開しない。

訴訟・権利紛争等の保全が必要な場合は対象/根拠/担当/見直し日を記録し、30日ごとに確認する。例外を理由に全データを無期限保存しない。法的な削除請求は通常の30日処理目標や作品保持ルールより優先して適用条件を確認する。[個人情報保護委員会の通則編](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)は、条件を満たす利用停止等の請求と利用不要な情報の扱いを確認する根拠であり、本提案の30/90/180日を指定するものではない。

## 退会処理の実装順（案）

- 受付：本人再確認、名義選択、保持対象/未完了表示、request ID。運営への代理依頼は本人確認を最小限にし、身分証を標準収集しない。
- 封じ込め：deletion_requested状態、新規API/直接DB/refresh拒否、公開profile停止。roleやDB権限の未整備を先に解消する。
- 一貫した整理：room creator/member approver/request deciderのNO ACTION FKを解決し、投稿/名義/公開author projectionと共同作品の扱いをtransactionで整える。posts.user_id NOT NULLや実Triggerを監査してから設計を確定する。
- 外部処理：Auth削除・Storage対象削除はDB transactionと別のため、再試行可能なjobで実施。段階ごとの完了証跡とgenericな利用者向け結果を分離する。
- 完了：Auth・profile・membership・public projection・署名経路・対象objectを照合してから通知。失敗はpending/failedのまま、再送でも共同作品を二重削除しない。

現在のaccount/deleteはprofiles.user_id/display_name/avatar_urlの不一致と部分成功問題がある。今回内部エラーの表示だけを抑制した。上記ライフサイクルを実装済みとは扱わない。

## 100人MVPの通報運用

おすすめは人手審査中心。責任者1名と代理1名を指名し、毎日10時/20時JSTを目安に確認する。24時間常時監視を約束しない。休暇/代理不在で確認できない期間は募集や公開を制限できる運用を用意する。

- 受付：アプリのroom/post通報に加え、未登録者・退会者・権利者が使える連絡窓口を設ける。現行アプリAPIはログイン必須なので代替窓口の実在確認が公開前必須。架空メールアドレスを掲載しない。
- 内部目標：24時間以内に一次確認。深刻な個人情報露出・安全上の危険・重大な権利侵害疑義は発見次第、必要範囲を暫定非表示。通常は72時間以内に初回判断、難件は7日以内に進捗連絡。法令上の期限とは別の目標。
- 状態：received→triaged→investigating→actioned/no_action→appealed→closed。担当/対象/根拠/次回期限/実行結果を持つ。現reports tableだけでこれらが管理できるとは確認していない。
- 証拠：対象ID、発生時刻、主張、必要最小限の該当箇所。申告者氏名/連絡先は相手へ原則共有しない。危険/違法な素材を無用に複製・ダウンロードしない。扱いに迷う案件は専門家へ。
- 判断：通報件数だけで自動削除/BANしない。同じ行為への基準を揃え、意見の相違と規約違反を区別する。標的型の大量通報や虚偽申告も審査する。
- 対処：注意→限定機能停止→一時停止→長期停止を基本にし、重大な安全上の案件は順序を飛ばして保護措置。表示非公開と物理削除を分け、他人の寄与を巻き込まない。
- 技術：非表示は一覧/詳細/未読/検索/署名/マーク/直接RESTへ一貫反映。既発行署名URLは期限まで有効な可能性があり、失効済みと誤案内しない。緊急時のobject隔離/CDN対応は承認手順と実検証が必要。
- 管理者：個人別アカウントとMFA、必要最小の権限。Service Roleを一般画面へ渡さず、共有keyで手作業を代用しない。削除/BANは対象・理由・承認者・結果を記録する。
- 通知：対象者に対象・理由・範囲・期間・異議窓口、申告者に受付/対応区分を知らせる。秘密・申告者情報・調査詳細の不要開示は避ける。
- 異議：通知から14日以内を通常窓口の目安とし、正当な後日申立てや法定権利を排除しない。原判断と別の担当が再確認し7日以内に進捗/結果連絡。誤りなら公開/権限/集計を復旧し記録する。

担当1名しか用意できない場合、利益相反案件/異議審査を本人だけで確定せず外部相談先を指定する。管理UIが無い間も、権限を限定した審査手順・記録・dry-runを先に作る。未検証のDashboard SQLをその場で実行する運用は推奨しない。

## 採用後の検収

合成ユーザーで、退会→公開profile不可/旧JWT拒否/共同作品維持/名義選択反映、creator退会→他人作品維持、Auth失敗→未完了/再試行、削除申立て→暫定非表示/署名拒否、誤通報→復旧、14日経過後の正当申立て、期限超過通知、バックアップ復元後の削除再適用を確認する。
物理削除・名義変更の正当性、共同制作への許諾継続、保持期限・法的請求の例外は専門家確認後に正式規約へ反映する。現行ユーザーに追加用途の同意を推定しない。

## ユーザーが決める最小項目

1. 共同作品を原則保持し、退会時に名義非表示を本人が確認する方式を採用するか。任意でペンネームのみ保持を認めるか。
2. 30日退会処理/90日通常証拠/180日再発防止見直しを初期案にするか（provider・法務確認後に公表）。
3. 責任者・代理・実在する連絡先。名前/連絡先はこの文書に推測で埋めない。

この3点の決定は本番適用の承認とは分ける。方針合意→schema/RPC/Trigger監査→ローカル実装→合成staging検収→規約/画面確定→別途本番承認の順。
